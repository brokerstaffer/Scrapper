Zillow Agent Scraper — How It Works

A Playwright-based Apify actor that extracts real-estate agent data from Zillow agent-search pages, with optional per-profile enrichment.

1. What it does in one sentence

You give it a list of locations (cities, neighborhoods, or ZIP codes). For each location it opens Zillow's "Find an Agent" results, scrolls through every agent in the list, and outputs one structured record per agent. Optionally, it then visits each agent's profile page to pull contact and business details.

Search URL pattern: zillow.com/professionals/real-estate-agent-reviews/<location-slug>/?page=N

2. The two-step pipeline

  1. Step 1 — Search page scrape (always runs) Loads the agent results page, slow-scrolls to force Zillow's virtualized list to render every agent, collects each agent's profile link + card text + headshot, and parses it into a record. Handles pagination up to Zillow's 25-page cap.
  2. Step 2 — Profile enrichment (only if enrichProfiles is ON) Visits each agent's profile page and fills in extra fields (phone, email, socials, license, etc.). It only fills empty fields — Step 1 data is never overwritten. If a profile fails to load, the Step 1 record is still saved.
How enrichment is decided: profiles are de-duplicated globally (an agent appearing in multiple locations/pages is only visited once). When maxProfilesPerLocation is set, only that many profiles per location are enriched; the rest are saved with Step 1 data only.

5. Anti-bot & reliability design

Staying under the radar

Concurrency = 1. Never opens more than one Zillow tab at a time.

Randomized delays between pages and profiles (with jitter).

Rotated user agents + browser fingerprinting per request.

Residential proxies with sticky-then-rotated sessions.

Robustness

Captcha detection: recognizes Zillow's "Press & Hold" / "confirm you're a human" pages, retires the session, and retries with a fresh one (up to 5 retries).

Bandwidth saving: blocks images, media, and fonts (~80% less proxy traffic; only text is needed).

Graceful degradation: if a profile fails, the Step 1 record is still saved.

6. How the data flows

locations[]  ─►  build search URL (page 1)
                     │
              ┌──────▼───────┐
              │  SEARCH page │  ◄── slow-scroll virtualized list,
              │   handler    │      collect links + card text + photo
              └──────┬───────┘
                     │  parse each agent card
                     │  de-dupe by profile URL
            ┌────────┴─────────┐
   enrich OFF │                │ enrich ON (under cap)
       save record       queue PROFILE request
                              │
                       ┌──────▼───────┐
                       │ PROFILE page │  ◄── __NEXT_DATA__ JSON + DOM scrape,
                       │   handler    │      fill only empty fields
                       └──────┬───────┘
                              │
                          save record
   (SEARCH handler also queues next page until maxPages / no next page)

7. Tech stack

Runtime: Node.js on the Apify platform · Crawler: Crawlee PlaywrightCrawler (headless Chromium)

Output: Apify Dataset (export to JSON / CSV / Excel) · Parsing: validated regex + DOM-segment parser

Source layout: main.js (orchestration) · routes.js (SEARCH/PROFILE handlers) · search-page.js (Step 1) · profile-page.js (Step 2) · parser.js (text parsing) · constants.js (columns, delays, helpers)
