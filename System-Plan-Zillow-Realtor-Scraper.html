SYSTEM PLAN · v1

Real-Estate Lead Scraping System

A web app where the client searches a ZIP code or location, runs Zillow & Realtor.com scrapers (Apify actors) on demand, and gets the results saved into their own system — searchable, viewable, and exportable.

1. Goal & scope

Build a self-serve tool for the client with a simple flow: type a location → pick a source → start scraping → get saved leads.

  • Search input: ZIP code or location name (city / neighborhood).
  • Sources: Zillow (actor already built ✅) and Realtor.com (actor to be built).
  • Trigger: the UI starts the matching Apify actor run for that search.
  • Storage: every scraped record is saved into the client's own database, tied to the search that produced it.
  • Output: client can browse, filter, and export the saved leads (CSV / Excel).

2. The big picture

① Frontend UI CLIENT FACING

Search form (location + source), "Start Scraping" button, live run status, results table, export buttons, run history.

② Backend API OUR SERVER

Receives the search, starts the right Apify actor, tracks the run, pulls results when finished, and saves them to the database.

③ Apify Actors SCRAPERS

Zillow actor + Realtor.com actor. They do the actual scraping on Apify's cloud (with residential proxies, anti-bot handling, etc.) and write results to an Apify Dataset.

④ Database CLIENT'S DATA

Stores users, searches/runs, and every scraped lead. This is the "saved in his system" part — data persists even after the Apify run is gone.

3. How a scrape works — end to end

  1. Client searches — enters a ZIP/location, selects Zillow and/or Realtor.com, sets options (e.g. max pages, enrich profiles), clicks Start Scraping.
  2. Backend creates a "Run" record in the database (status = RUNNING) and calls the Apify API to start the chosen actor with the search input.
  3. Apify runs the actor on its cloud — scrolling pages, handling captchas/proxies, parsing each listing/agent into structured records, and pushing them to that run's Dataset.
  4. Apify notifies the backend when the run finishes — via a webhook (preferred) or the backend polls the run status.
  5. Backend fetches the dataset from Apify (the full list of scraped records) using the Apify API.
  6. Backend saves the leads into the database, linked to that Run, de-duplicating against existing records.
  7. UI updates — the run shows COMPLETED with a result count; the client can view, filter, and export the leads.
Key point on "the data comes from Apify": yes — Apify is where the scraping happens and where results first land (the Dataset). Our backend then copies that data into the client's own database so it's permanent, searchable, and independent of Apify's storage retention.
Apify model — rented actors: we publish both actors on the Apify Store as rental (paid) actors. The client rents them from their own Apify account — they pay a monthly rental fee for access plus their own Apify platform usage (proxies + compute). Nothing scraping-related is billed to us; everything runs under the client's account. The backend triggers runs using the client's API token (stored securely server-side).

5. Components in detail

Frontend UI React / Next.js

  • Search page: location input (ZIP or name), source toggle (Zillow / Realtor.com / both), advanced options (max pages, enrich profiles, max profiles).
  • Run status: live progress — "Scraping… 120 found so far", with states QUEUED → RUNNING → COMPLETED / FAILED.
  • Results table: paginated, sortable, filterable (by city, rating, has-phone, source, etc.).
  • Export: download current view as CSV / Excel.
  • History: list of past searches/runs with counts and timestamps; re-open or re-run.

Backend API Node.js (Express/Nest) or Next API routes

Holds the client's Apify API token (stored server-side, never exposed to the browser), orchestrates runs, and persists data.

EndpointPurpose
POST /api/scrapeStart a scrape — creates a Run, calls Apify to start the actor
GET /api/runsList the client's runs (history) with status + counts
GET /api/runs/:idRun detail + live status
POST /api/webhooks/apifyApify calls this when a run finishes → backend pulls + saves data
GET /api/leadsQuery saved leads (filter / paginate / search)
GET /api/leads/exportStream CSV / Excel of filtered leads

Apify Actors the scrapers

Two ready-made Apify actors do the scraping — one for each source. Both take a location input and output structured records to an Apify Dataset.

Zillow actor

Searches agents by location, scrapes the results list, and optionally enriches each profile. Outputs structured agent records to a Dataset.

Realtor.com actor

Takes a location input → scrapes Realtor.com listings/agents → outputs structured records to a Dataset, the same way the Zillow actor does.

Standardize the output: both actors should emit a common field set (name, contact, location, source, source URL, …) so the database and UI treat all leads uniformly regardless of source. A source column (zillow / realtor) distinguishes them.

Database PostgreSQL (e.g. Supabase)

Three core tables. Supabase is a good fit since it gives Postgres + auth + an API out of the box.

users            ── id, email, name, created_at

runs             ── id, user_id, source ('zillow'|'realtor'),
                    location, options(jsonb),
                    apify_run_id, status, result_count,
                    started_at, finished_at

leads            ── id, run_id, user_id, source,
                    name, brokerage, phone, email,
                    rating, review_count,
                    location, city, state, zip,
                    profile_url, photo_url,
                    raw(jsonb),            -- full original record
                    created_at
                    UNIQUE(user_id, source, profile_url)  -- de-dupe

7. Integration with Apify (the important bit)

Start a run — backend calls Apify with the actor ID and the search as input:

POST https://api.apify.com/v2/acts/{ACTOR_ID}/runs?token=APIFY_TOKEN
{
  "locations": ["80542"],        // or ["Boulder, CO"]
  "enrichProfiles": true,
  "maxPages": 5
}
// → returns { data: { id: RUN_ID, defaultDatasetId: DATASET_ID, ... } }

Get results when finished:

GET https://api.apify.com/v2/datasets/{DATASET_ID}/items?token=APIFY_TOKEN
// → array of scraped lead records → save to DB

Get notified — register a webhook so Apify pings the backend the moment a run succeeds, instead of polling:

eventTypes: ["ACTOR.RUN.SUCCEEDED", "ACTOR.RUN.FAILED"]
requestUrl:  https://yourapp.com/api/webhooks/apify
Two ways to know a run finished — use webhooks for production (instant, efficient). Keep polling (GET /v2/actor-runs/{id} every few seconds) as a simple fallback for early development.

8. Build phases

  1. Phase 1 — Foundation: set up DB schema (users/runs/leads), Supabase auth, and the backend skeleton with the Apify token.
  2. Phase 2 — Zillow end-to-end: wire the UI search → start the Zillow actor → save results → show in a table + export. Proves the whole pipeline.
  3. Phase 3 — Add Realtor.com: plug in the Realtor.com actor, standardize its output fields, and add the source selector + unified leads view across both sources.
  4. Phase 4 — Polish: run history, filtering, de-dupe, error handling, webhooks, usage limits.

9. Things to decide / watch

Decisions needed

  • Single client or multiple users/accounts?
  • Rental price & terms for each actor (monthly fee, trial?).
  • Any limits (max scrapes/day, max pages) to control proxy cost?
  • Export format priorities (CSV, Excel, Google Sheets, CRM push?).

Watch-outs

  • Cost: residential proxy + compute is billed per run — surface estimated cost / result counts.
  • Long runs: big locations can take minutes — UI must handle async, not block.
  • De-dupe: same agent across ZIPs/sources — unique key on profile URL.
  • Compliance: respect each site's terms; this is for the client's authorized use.
